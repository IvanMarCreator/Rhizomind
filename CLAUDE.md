# Rhizomind — правила работы агента

Rhizomind — локальное десктопное приложение для базы знаний из связанных Markdown-заметок (опыт как в Obsidian, свой продукт). Сейчас разрабатывается **Secure-редакция**: её цель — пройти согласование службы ИБ в компании, где Obsidian отклонили из-за синхронизации и выходов в сеть. Стек: Tauri 2 — ядро на Rust, интерфейс Svelte 5 + TypeScript в системном WebView (ADR 0008); сначала Windows, код кроссплатформенный. Лицензия GPL-3.0.

## Инварианты Secure-редакции

Это жёсткие правила. Любое решение, которое их задевает, сначала обсуждается с пользователем.

1. **Доказуемо нет сети.** В коде приложения нет сетевых возможностей вообще, а не выключенных. Внешняя ссылка из заметки передаётся системному браузеру только после подтверждения пользователя. Встроенного браузера, загрузок, телеметрии, автообновлений, плагинов нет.
2. **Контур хранилища и учёт локальных записей.** Заметки и служебные данные хранилища (настройки, индекс, раскладка, темы, журнал ошибок) лежат внутри хранилища, служебные — в `.rhizomind/`. Главная цель — данные не уходят в сеть и в синхронизацию. Записи вне хранилища на этом компьютере допустимы (решение владельца 45, 25.10.2026), если: (а) они не попадают в сеть и в синхронизируемые места (OneDrive и подобные, перемещаемый профиль Windows `%APPDATA%\Roaming`); (б) каждая учтена в `docs/SECURITY.md`, раздел «Записи вне хранилища»: где, что содержит, кто пишет, когда удаляется; (в) автоматическая проверка следов ловит новые неучтённые записи. Имена и содержимое заметок вне хранилища не пишутся. Служебные файлы браузерного движка (WebView2) — во временной папке, которая удаляется при выходе (ADR 0007). Хранилище на флешке допустимо: какие носители подключаются, решает политика компании.
3. **Браузерный движок ничего не сохраняет.** Сессия только в памяти, дампов падений нет. Журнал ошибок — без содержимого заметок, с ограничением размера.
4. **Без потери данных.** Приложение не затирает изменения, сделанные в файлах снаружи: если файл изменился одновременно в приложении и снаружи, сохраняются обе версии. Внешнее действие считается действием пользователя: удаление открытой заметки снаружи закрывает её, несохранённый ввод не восстанавливается. Удаление — в корзину ОС; на диске без корзины (флешка, сетевая папка) — безвозвратно, только после отдельного подтверждения.
5. **Доказательства для ИБ.** Каждое изменение, касающееся сети, файлов или хранения, отражается в `docs/SECURITY.md` со ссылкой на файл с реализацией.

## Процесс

Каждый выпуск и каждая крупная функция проходят три шага. Код пишется только после двух утверждений.

1. **Спецификация** в `docs/specs/`: что строим, границы, решения, критерии приёмки. Пользователь утверждает.
2. **План** в `docs/plans/`: задачи, у каждой проверяемый критерий готовности (тест, команда и ожидаемый вывод). Пользователь утверждает план и способ выполнения.
3. **Реализация** по задачам плана силами субагентов (см. «Оркестрация»).
4. **Ручная проверка владельцем:** выпуск и каждая крупная функция доходят до пользователя рабочей сборкой с коротким списком того, что проверить.

Работа идёт маленькими шагами: функция сначала делается в минимальном виде, проверяется и обкатывается, потом расширяется.

Внутри задачи:
- сначала красный тест, потом код (`mattpocock-skills:tdd`);
- ошибка, упавший тест или медленная работа — цикл диагностики (`mattpocock-skills:diagnosing-bugs`);
- «готово» подтверждается запущенной командой и её выводом в отчёте;
- после задачи — ревью кода по стандартам и спецификации (`mattpocock-skills:code-review`) и ревью безопасности по инвариантам выше.

Термины предметной области — в `CONTEXT.md`, архитектурные решения — ADR в `docs/adr/` (оба через `mattpocock-skills:domain-modeling`). Границы модулей и API ядра проектируются через `mattpocock-skills:codebase-design`. Макеты интерфейса по просьбе пользователя — в Figma через skills `figma:*`. Устойчивые предпочтения пользователя записываются через `task-observer`.

## Оркестрация

Основной агент — **оркестратор**: ведёт разговор с пользователем, держит план и раздаёт работу субагентам. Его продукт — постановка задач, сборка результатов и приёмка; код он пишет сам только в мелочах.

- **Роли субагентов:** исследователь (факты из первоисточников: версии, лицензии, сетевые вызовы в зависимостях), разработчик, QA (тесты, критерии приёмки, проверка на тестовом хранилище), дизайнер (интерфейс, макеты в Figma), ревьюер безопасности (сверка с инвариантами), ревьюер кода.
- **Параллельно** — всё независимое: исследования разных вопросов, задачи плана без общих файлов, QA и ревью готовой задачи. Независимые субагенты запускаются в одном ходе, без ограничения числа; зависимые — по очереди.
- **Постановка задачи:** субагент начинает с нуля, поэтому получает цель, ссылки на нужные документы (этот файл, требования, спецификацию, задачу плана), границы (какие файлы трогать), критерий готовности и формат отчёта.
- **Разделение файлов:** разработчики, работающие одновременно, получают непересекающиеся файлы или отдельные рабочие копии (git worktree).
- **Временные файлы и сборка:** у каждого субагента своя подпапка `scratchpad/<задача>/`; общих имён файлов в корне scratchpad нет; git — только с явным `git -C <своя рабочая копия>`. Диск облачной машины ограничен: параллельные задачи используют общую папку сборки Rust (`CARGO_TARGET_DIR=/home/claude/cargo-shared-target`), закрытые рабочие копии удаляются сразу после слияния. Общая папка сборки может подмешать результат сборочного скрипта чужой ветки (файлы `src-tauri/permissions/autogenerated/`): перед проверками Rust — `touch src-tauri/build.rs src-tauri/src/commands/list.rs`.
- **Без принудительной отправки:** среда запрещает `push --force`; ветка совмещается с `main` коммитом слияния.
- **Приёмка:** оркестратор принимает результат по команде и её выводу. QA и ревью делает не тот субагент, который писал код.
- **QA глазами:** QA-агент смотрит снимки экрана из сценарных тестов и сравнивает с ожидаемым (спецификация, макет Figma). Перед каждой сборкой для пользователя QA-агент проходит чек-лист на компьютере пользователя через управление экраном (с его разрешения) и сдаёт отчёт «ожидалось / получилось» со снимками.
- **Дизайн:** дизайнер-агент работает в Figma (skills `figma:*`), каждый вариант — сразу в светлой и тёмной теме; пользователь получает ссылки и превью и выбирает.
- **Машины:** работоспособность проверяется на компьютере пользователя; скорость, слабая графика, сетевой аудит и установщик — пользователем вручную на второй машине по пошаговой инструкции.
- **Пользователю** — итог, а не переписка субагентов: оркестратор пересказывает результат и выносит на решение то, что решает пользователь.

## Пользователь и общение

- Пользователь — владелец продукта: даёт идеи, утверждает спецификации, планы и результат. Весь код пишет агент.
- Общение на русском, простыми словами; термин объясняется при первом упоминании.
- Решения обсуждаются **блоками нумерованных вопросов с вариантами ответа**: 2–3 варианта, плюсы и минусы, рекомендация.
- Пользователь часто диктует голосом: опечатки распознавания («двойные кавычки» вместо «квадратные скобки», «eBay» вместо «ИБ») понимаются по смыслу.
- Спорные места и конфликты с инвариантами называются прямо, с вариантами и рекомендацией.

## Окружение

- Основной репозиторий — GitHub `IvanMarCreator/rhizomind`, ветка `main`. Агенты работают в облачной копии: задача — отдельная ветка `task/<номер>-<кратко>`, оркестратор проверяет и сливает в `main`.
- `gh` в облачной среде не авторизован: pull request и настройки репозитория через API недоступны. Git push работает.
- `D:\Rhizomind` на компьютере пользователя — локальная копия; обновляется через `git pull`. Через удалённую оболочку на этом компьютере git не запускать: удаление файлов там запрещено, и git оставляет lock-файлы, которые ломают репозиторий.

## Документы

- `docs/product/requirements.md` — что строим, план выпусков; перед спецификацией и планом.
- `CONTEXT.md` — словарь терминов; при именовании модулей, сущностей, текстов интерфейса.
- `docs/SECURITY.md` — модель безопасности для ИБ; при изменении сети, файлов, хранения.
- `docs/ARCHITECTURE.md` — обзор архитектуры и список решений; при проектировании и перед спецификацией.
- `CHANGELOG.md` — изменения по версиям; пополняется каждой задачей, попадает в описание выпуска в GitHub Releases.
