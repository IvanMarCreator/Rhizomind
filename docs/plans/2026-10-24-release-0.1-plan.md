# План реализации выпуска 0.1 «Основа»

Статус: **утверждён владельцем 24.10.2026** с ответами на П1–П4 (раздел 5).
Спецификация: [docs/specs/2026-10-24-release-0.1-osnova.md](../specs/2026-10-24-release-0.1-osnova.md) (дальше — «спецификация», разделы как «С3.4»).

## 1. Как выполняется

### 1.1. Где идёт работа
- Код живёт в репозитории на GitHub. Субагенты работают в облаке, каждый в своей ветке, и сдают задачу запросом на слияние (pull request).
- **Сборка и тесты на Windows** — в GitHub Actions на машине `windows-latest`: там проверяется всё, что зависит от Windows (слежение за папкой на NTFS, точки соединения, корзина, установщик). Быстрые тесты дополнительно идут на Linux.
- Ветка `main` защищена: слияние только при зелёной проверке и после ревью.
- Портативные сборки и установщики собирает GitHub Actions; владелец скачивает их со страницы сборки или из GitHub Releases.
- Локальная папка `D:\Rhizomind` получает изменения через `git pull`.
- **Компьютер владельца с Windows** (подключён к сессии) — основная машина для проверки работоспособности: QA-агент запускает на нём портативную сборку и проходит сценарии через управление экраном, с разрешения владельца.
- **Вторая машина без отдельной видеокарты** — скорость, граф, нефункциональные проверки, ручной сетевой аудит и установщик; проверяет владелец по пошаговым инструкциям и присылает обратную связь.

### 1.2. Правила для каждой задачи
- Сначала красный тест, потом код (`mattpocock-skills:tdd`). Отказ теста или медленная работа — цикл диагностики (`mattpocock-skills:diagnosing-bugs`).
- Задача сдаётся с командами проверки и их выводом. Критерий готовности — строка «Готово, когда» у задачи; общий для всех: `npm run verify` зелёный в CI на Windows и Linux.
- После задачи — ревью кода (`mattpocock-skills:code-review`) другим субагентом. Задачи с пометкой 🔒 дополнительно проходят ревью безопасности по инвариантам `CLAUDE.md`.
- Каждая задача пополняет `CHANGELOG.md`; задачи 🔒 — ещё и `docs/SECURITY.md` со ссылкой на файл.
- Новая зависимость — только с проверкой: лицензия совместима с GPL-3.0, нет сетевого кода и телеметрии, версия зафиксирована точно. Решение записывается в `docs/dependencies.md`.

### 1.3. Роли
Оркестратор (основной агент) раздаёт задачи, сливает ветки, ведёт этот план и общается с владельцем. Субагенты: разработчик, QA, дизайнер, ревьюер кода, ревьюер безопасности. Число одновременных субагентов не ограничено — столько, сколько независимых задач.

**QA проверяет глазами, а не только тестами.**
- Сценарные тесты в CI на Windows делают снимки экрана на каждом шаге; QA-агент смотрит их и сравнивает с ожидаемым результатом из спецификации и с макетом Figma, неожиданное описывает с указанием снимка.
- Перед каждой контрольной точкой QA-агент запускает портативную сборку на компьютере владельца, проходит чек-лист через управление экраном и сдаёт отчёт со снимками «ожидалось / получилось».
- Владелец получает сборку только после такого прохода.

**Дизайн — в Figma.** Дизайнер-агент делает варианты в Figma, сразу в светлой и тёмной теме; владелец получает ссылки и превью и выбирает по каждому решению.

### 1.4. Маленькие шаги и сборки для владельца
Три контрольные точки, на каждой владелец получает портативную сборку и короткий список «что проверить»:
- **КТ1 «Оболочка»** — окно, хранилище, дерево, простой редактор с автосохранением.
- **КТ2 «Заметки»** — живой предпросмотр, режим исходного текста, вики-ссылки, Ctrl+O, история.
- **КТ3 «Кандидат 0.1»** — всё из спецификации, приёмка по С9.

## 2. Задачи

Обозначения: **Роль** — кто делает; **Файлы** — где работает (параллельные задачи не пересекаются по файлам); **После** — от каких задач зависит.

### Этап 0. Основа репозитория

**0.1. Репозиторий и CI** — разработчик.
Файлы: `.github/`, корень репозитория. После: —.
Первый коммит текущих документов и прототипа (для истории), затем прототип переезжает в `prototype/` как справочник. Workflow GitHub Actions: Windows и Linux, кэш зависимостей, защищённая `main`.
Готово, когда: пробный запрос на слияние проходит CI на обеих ОС.

**0.2. Каркас приложения** — разработчик.
Файлы: `package.json`, `src/main/`, `src/preload/`, `src/renderer/`, конфигурации. После: 0.1.
Electron 45.0.x, TypeScript strict, Vite 8, Svelte 5, Vitest, Playwright для Electron; точные версии и lock-файл. Скрипты: `dev`, `test`, `test:e2e`, `verify` (типы + линтер + тесты + проверка сети + лицензии), `package:portable`, `package:installer`, `sbom`. Пустое окно открывается через протокол `app://`.
Готово, когда: в CI на Windows `npm run verify` зелёный, сценарный тест «окно открылось» проходит, `npm run package:portable` даёт zip, который запускается.

**0.3. Безопасная оболочка** 🔒 — разработчик.
Файлы: `src/main/security/`. После: 0.2.
Сетевой выключатель на всех сессиях (включая сессию по умолчанию), партиция без записи на диск, временная папка Chromium с удалением при выходе и уборкой остатков при запуске, ключи Chromium (`--no-proxy-server`, `--host-resolver-rules`, `--disable-http-cache`, `--disable-gpu-shader-disk-cache`), словари орфографии отключены, обработчик падений не запускается, CSP, запреты навигации, окон, загрузок, разрешений, Electron Fuses. Проверка исходников на сетевой код расширяется на зависимости, которые попадают в сборку. (ADR 0007, С6.)
Готово, когда: сценарный тест считает запросы за пределы `app://` — ноль; тест следов в CI на Windows: во время работы вне хранилища пишутся только `vaults.json` и временная папка, после выхода временной папки нет.

**0.4. Контракт API ядра и интерфейсы модулей** — оркестратор с `mattpocock-skills:codebase-design`.
Файлы: `src/shared/api.ts`, `src/shared/`, интерфейсы в `src/main/*/index.ts`. После: 0.2.
Типы API ядра v1 (С5.5), событий, версии файла, интерфейсы модулей ядра (С5.2) и заглушка API для разработки интерфейса без ядра.
Готово, когда: типы компилируются, заглушка API проходит тесты контракта; владелец не участвует.

### Этап 1. Ядро (задачи 1.1–1.6 идут параллельно после 0.4)

**1.1. Общая логика ссылок и имён** — разработчик.

Правила имён Windows (С3.2), нормализация и сравнение имён, разбор вики-ссылок, кратчайший различающий путь (С3.4, включая случай корня `[[/Встреча]]`), разрешение ссылок (с путём, без пути, самая старая при дубликатах), естественная сортировка по-русски.
Готово, когда: модульные тесты покрывают каждое правило С3.2 и С3.4 с русскими именами, регистром и Unicode.

**1.2. Хранилище: файлы и контур** 🔒 — разработчик.
Файлы: `src/main/vault/`. После: 0.4.
Контур (пути, символические ссылки, точки соединения NTFS), чтение с версией файла, атомарная запись через `.rhizomind/tmp/` с проверкой ожидаемой версии, сохранение BOM и переносов строк, лимит размера из настроек (больше лимита — только чтение), операции с деревом, корзина ОС, `settings.json` и `workspace.json` с версией формата.
Готово, когда: модульные тесты и тесты на Windows в CI: выход за контур невозможен ни одним способом из списка; набор образцов (CRLF, LF, BOM, без BOM) открывается и сохраняется байт в байт; сбой посреди записи оставляет заметку целой.

**1.3. Список хранилищ и окна** 🔒 — разработчик.
Файлы: `src/main/registry/`, `src/main/windows/`. После: 0.4.
`vaults.json` (единственный файл в профиле), открытие хранилища в новом окне, фокус на уже открытое, запоминание размера окна и последнего хранилища.
Готово, когда: тесты проверяют формат файла и что в нём нет ничего, кроме имён, путей и состояния окон.

**1.4. Слежение за папкой** 🔒 — разработчик.
Файлы: `src/main/watcher/`. После: 0.4.
`@parcel/watcher` за интерфейсом, исключение `.rhizomind`, сверка при открытии, перепроверка после переполнения, отличие своих записей по версии файла, распознавание переименования и перемещения (идентификатор файла NTFS, запасной путь — размер и хэш). (ADR 0006.)
Готово, когда: автотесты под нагрузкой в CI на Windows (С8): 10 000 файлов пачкой, массовая замена как при `git checkout`, переименования, искусственное переполнение — после затихания событий модель совпадает с диском, свои записи не считаются внешними.

**1.5. Внешние ссылки** 🔒 — разработчик.
Файлы: `src/main/links/`. После: 0.4.
Окно подтверждения в ядре с полным адресом, только `http`, `https`, `mailto`. (С3.7.)
Готово, когда: тесты — без подтверждения адрес не уходит в ОС; другие схемы отклоняются.

**1.6. Генератор тестового хранилища** — QA.
Файлы: `tools/gen-vault/`. После: 0.2.
Хранилище на N заметок со ссылками, псевдонимами, дубликатами имён, вложенными папками, картинками и PDF-заглушками, образцами CRLF/LF/BOM.
Готово, когда: `npm run gen:vault -- --notes 10000` создаёт хранилище, проверка состава проходит.

**1.7. Мост и обработчики API** 🔒 — разработчик.
Файлы: `src/preload/`, `src/main/ipc/`. После: 1.2–1.5.
`window.rhizomind` по контракту 0.4, проверка отправителя и типов всех параметров, события.
Готово, когда: тесты контракта проходят на настоящем ядре; вызов с чужой страницы или с неверными типами отклоняется.

## 4. Риски

| Риск | Что делаем |
|---|---|
| `@parcel/watcher` или Electron 45 ведут себя на Windows не так, как в документации | Задачи 1.4 и 0.3 первыми в CI на Windows; запасной вариант слежения — chokidar за тем же интерфейсом |
| Chromium пишет в профиль что-то сверх найденного | Тест следов в 0.3 с первого дня; находки — в ADR 0007 и `SECURITY.md` |
| Живой предпросмотр с русским вводом (IME) ведёт себя неожиданно | Шаг 2.5 отдельно от сохранения; КТ2 — ручная проверка владельцем |
| Корпоративная политика не даёт запустить неподписанную портативную сборку | Проверка на другой машине; установщик через службу ИТ |
| Конфликты слияния при параллельной работе | Непересекающиеся папки у параллельных задач; оркестратор сливает по одной ветке |

## 5. Решения владельца по плану
- П1: репозиторий на GitHub (владелец создаёт и присылает ссылку), CI на Windows и Linux.
- П2: число субагентов не ограничено.
- П3: дизайн в Figma, варианты по каждому решению, светлая и тёмная тема одновременно.
- П4: работоспособность — на компьютере владельца; скорость, машина без видеокарты, сетевой аудит и установщик — вручную на второй машине.
