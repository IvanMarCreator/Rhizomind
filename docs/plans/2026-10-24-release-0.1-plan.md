# План реализации выпуска 0.1 «Основа»

Статус: **утверждён владельцем 24.10.2026** (переход на Tauri).
Спецификация: [docs/specs/2026-10-24-release-0.1-osnova.md](../specs/2026-10-24-release-0.1-osnova.md), ревизия 5 (дальше — «спецификация», разделы как «С3.4»). Решения: [ADR 0006](../adr/0006-watcher-notify.md), [ADR 0007](../adr/0007-webview2-traces-network.md), [ADR 0008](../adr/0008-platform-tauri2.md), [ADR 0009](../adr/0009-tauri-boundary-security.md).

## 1. Как выполняется

### 1.1. Где идёт работа
- Код живёт в репозитории на GitHub. Субагенты работают в облаке, каждый в своей ветке, и сдают задачу запросом на слияние (pull request).
- **Сборка и тесты на Windows** — в GitHub Actions на машине `windows-latest`: там проверяется всё, что зависит от Windows (WebView2, слежение за папкой на NTFS, точки соединения, корзина, установщики). Тесты ядра и сценарии дополнительно идут на `ubuntu-latest`.
- Ветка `main` защищена: слияние только при зелёной проверке и после ревью.
- Портативные сборки и установщики собирает GitHub Actions; владелец скачивает их со страницы сборки или из GitHub Releases.
- Локальная папка `D:\Rhizomind` получает изменения через `git pull`.
- **Компьютер владельца с Windows** (подключён к сессии) — основная машина для проверки работоспособности: QA-агент запускает на нём портативную сборку и проходит сценарии через управление экраном, с разрешения владельца.
- **Вторая машина без отдельной видеокарты** — скорость, граф, нефункциональные проверки, ручной сетевой аудит и установщики; проверяет владелец по пошаговым инструкциям и присылает обратную связь.

### 1.2. Правила для каждой задачи
- Сначала красный тест, потом код (`mattpocock-skills:tdd`). Отказ теста или медленная работа — цикл диагностики (`mattpocock-skills:diagnosing-bugs`).
- Задача сдаётся с командами проверки и их выводом. Критерий готовности — строка «Готово, когда» у задачи; общий для всех: `npm run verify` зелёный в CI на Windows и Linux. `verify` включает `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`, `cargo deny check`, проверку `cargo tree` по целям, проверку типов и линтер интерфейса, Vitest, проверку интерфейса на сетевой код и лицензии npm.
- После задачи — ревью кода (`mattpocock-skills:code-review`) другим субагентом. Задачи с пометкой 🔒 дополнительно проходят ревью безопасности по инвариантам `CLAUDE.md` и ADR 0007, 0009.
- Каждая задача пополняет `CHANGELOG.md`; задачи 🔒 — ещё и `docs/SECURITY.md` со ссылкой на файл.
- Новая зависимость (крейт или пакет npm) — только с проверкой: лицензия совместима с GPL-3.0, нет сетевого кода и телеметрии, версия зафиксирована точно, `cargo deny check` проходит. Решение записывается в `docs/dependencies.md`.

### 1.3. Роли
Оркестратор (основной агент) раздаёт задачи, сливает ветки, ведёт этот план и общается с владельцем. Субагенты: разработчик, QA, дизайнер, ревьюер кода, ревьюер безопасности. Число одновременных субагентов не ограничено — столько, сколько независимых задач.

**QA проверяет глазами, а не только тестами.**
- Сценарные тесты (tauri-driver + WebDriver) в CI на Windows делают снимки экрана на каждом шаге; QA-агент смотрит их и сравнивает с ожидаемым результатом из спецификации и с макетом Figma, неожиданное описывает с указанием снимка.
- Перед каждой контрольной точкой QA-агент запускает портативную сборку на компьютере владельца, проходит чек-лист через управление экраном и сдаёт отчёт со снимками «ожидалось / получилось».
- Владелец получает сборку только после такого прохода.

**Дизайн — в Figma.** Дизайнер-агент делает варианты в Figma, сразу в светлой и тёмной теме; владелец получает ссылки и превью и выбирает по каждому решению.

### 1.4. Маленькие шаги и сборки для владельца
Три контрольные точки, на каждой владелец получает портативную сборку и короткий список «что проверить»:
- **КТ1 «Оболочка»** — окно, хранилище, дерево, простой редактор с автосохранением.
- **КТ2 «Заметки»** — живой предпросмотр, режим исходного текста, вики-ссылки, Ctrl+O, история.
- **КТ3 «Кандидат 0.1»** — всё из спецификации, приёмка по С9.

## 4. Риски

| Риск | Что делаем |
|---|---|
| `notify` 9 (кандидат в выпуск) на Windows ведёт себя не так, как в исходниках | Задача 1.4 и нагрузочные тесты — первыми в CI на Windows; запасной путь — свой наблюдатель на крейте `windows` за тем же интерфейсом (ADR 0006) |
| WebView2 пишет что-то вне папки данных или флаги против фоновой сети не действуют (для WebView2 они не документированы) | Тест следов в 0.3 с первого дня; сетевой аудит в 3.3; флаг без подтверждённого действия не заявляется гарантией; находки — в ADR 0007 и `SECURITY.md` |
| Своя правка wry расходится с новыми версиями Tauri | Правка в одно свойство, версия wry зафиксирована; при обновлении Tauri правка переносится и проверяется интеграционным тестом 0.3; предложение авторам wry, чтобы убрать правку |
| ИБ отклоняет выпуск из-за обращений системной версии WebView2 к Microsoft | Обращения честно описаны в `SECURITY.md` вместе с политиками для ИТ; к встроенной версии с правилом брандмауэра возвращаемся только в этом случае (ADR 0007) |
| Сценарные тесты через tauri-driver нестабильны или медленны в CI; на macOS tauri-driver нет | Основная проверка интерфейса — Vitest с подменой команд; WebDriver — только сценарии С3; macOS — при переходе на эту ОС |
| Долгая сборка Rust в CI | Кэш `Swatinem/rust-cache`, раздельные задания проверок и сборки |
| Живой предпросмотр с русским вводом (IME) ведёт себя неожиданно | Шаг 2.5 отдельно от сохранения; КТ2 — ручная проверка владельцем |
| Корпоративная политика не даёт запустить неподписанную портативную сборку или поставить NSIS в профиль | Проверка на другой машине; MSI через службу ИТ |
| Конфликты слияния при параллельной работе | Непересекающиеся папки у параллельных задач; общие файлы — у оркестратора; оркестратор сливает по одной ветке |

## 5. Решения владельца по плану
- П1: репозиторий на GitHub (владелец создаёт и присылает ссылку), CI на Windows и Linux.
- П2: число субагентов не ограничено.
- П3: дизайн в Figma, варианты по каждому решению, светлая и тёмная тема одновременно.
- П4: работоспособность — на компьютере владельца; скорость, машина без видеокарты, сетевой аудит и установщики — вручную на второй машине.
