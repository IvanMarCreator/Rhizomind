# План выпуска 0.3 «Скорость»

План и выполнение разработчиками с независимым QA утверждены владельцем 26.11.2026. [Спецификацию](../specs/2026-11-26-release-0.3-skorost.md) владелец утвердил. Разработчики работают по сценариям в отдельных ветках. Один независимый QA получает перечисленные ниже проверки перед каждым слиянием. Первыми до рабочей сборки доходят F12 и шаблоны. Затем идут поиск, вставка вложений и их просмотр.

## Порядок работы

Каждый пункт начинается с воспроизведения в тесте. Разработчик прикладывает команду, наблюдавшийся сбой до реализации и результат после. QA проверяет тот же коммит через обычный интерфейс, сравнивает результат с диском, проверяет ошибки и регрессии. Для пользовательского интерфейса нужны клавиатура, светлая и тёмная темы и снимки окна. Для файловых операций нужны проверки границ ядра на Windows и Linux. Результаты собираются в одном отчёте выпуска. Изменения возможностей, сети и хранения сопровождаются правками в [SECURITY.md](../SECURITY.md) и CHANGELOG.

### 1. Палитра команд

- [ ] Проверить компонентным тестом открытие F12 из редактора и дерева, ввод части русского названия, перемещение стрелками и однократный вызов по Enter. При Esc возвращаются исходные фокус и выделение. В действующем модальном окне фокус остаётся внутри.
- [ ] Подключить палитру к существующим командам и пользовательским назначениям в `src/settings/hotkeys.ts`, ограничениям `src/shell/engineShortcuts.ts` и диспетчеризации окна. В списке видны подпись, текущее сочетание и доступность действия в исходном контексте. Создание заметки, переключение режима, история, правая панель и действия дерева выполняют соответствующую команду приложения.
- [ ] QA запускает `npm test -- palette hotkeys engineShortcuts` и сценарий `npm run test:e2e -- palette`. Проверяет F12 при русской раскладке, переназначенное сочетание после обновления, Enter, Esc, Ctrl+O, Ctrl+N и F2 в дереве. Ожидаются один вызов выбранного действия, прежние действия клавиш и сохранённый текст.

### 2. Создание из шаблона

- [ ] Добавить настройку папки шаблонов открытого хранилища через `src/settings/sections/FilesSection.svelte` и `src-tauri/src/vault/settings.rs`. Проверить чтение настроек 0.2 и показ выбора папки при первом вызове. Перечислять вложенные Markdown-файлы с различающими путями.
- [ ] Зарегистрировать в палитре «Создать из шаблона» и в ядре операцию копирования. Применить действующую настройку места новых заметок и проверку контура в `src-tauri/src/vault`. Копия создаётся целиком под свободным именем без перезаписи и открывается обычным механизмом открытия. При гонке за одно имя существующий файл сохраняется.
- [ ] QA выполняет `cargo test -p rhizomind --locked template`, `npm test -- template` и `npm run test:e2e -- template`. Сравнивает исходник и результат побайтно для BOM, CRLF, свойств, ссылок и буквального `{{дата}}`. Проверяет два одинаковых имени в разных папках, три режима назначения, удалённый шаблон, отмену, занятое имя и носитель только для чтения. Владелец получает сборку для проверки полного пути F12 → шаблон → новая заметка.

### 3. Поиск по хранилищу

- [ ] Начать с контрольных заметок для русских словоформ, одинаковых заголовков, совпадения в тексте, тега из свойств, папки и похожего префикса. Зафиксировать один тип запроса для ядра и интерфейса со словами, папкой, тегом и режимом упоминаний. Полное название идёт первым. Текстовое совпадение возвращает путь и актуальную строку, совпадение только в названии открывает заметку.
- [ ] Сохранить интерфейс индекса 0.2 для связей. В `src-tauri/src/index` реализовать одну производную базу `.rhizomind/index.db` с FTS5 по [ADR 0004](../adr/0004-index-staged.md). Хранить производные токены и позиции. Сниппет перечитывается из Markdown. Проверить повторное открытие, переход с `index.json`, восстановление из повреждённой базы, внешние изменения, переименование и удаление. Отказ индекса не должен лишать доступа к заметкам.
- [ ] Подключить экран поиска через палитру и `src/api/commands.ts`. Отбрасывать запоздавшие ответы и показывать ход индексации. В режиме «Упоминания без ссылки» пропускать существующие ссылки и показывать обычное упоминание на реальной строке. Сохранить Ctrl+O и назначение Ctrl+F.
- [ ] QA запускает `cargo test -p rhizomind --locked search`, `npm test -- search` и `npm run test:e2e -- search`. Запрос «проверка» находит «после проверки» и пропускает «перепроверка». Запрос из двух слов исключает заметку, в которой только одно из них. Фильтр папки «Работа» включает «Работа/Квартал» и исключает «Работа-архив»; тег дополнительно ограничивает результаты. После внешней правки переход приводит к совпадению в текущем тексте. После пересборки результаты совпадают с контрольным набором, ранее существовавшие обратные ссылки и теги остаются доступны.
- [ ] В тесте сборки проверить FTS5, `SQLITE_TEMP_STORE=3`, `SQLITE_OMIT_LOAD_EXTENSION`, фактический `PRAGMA temp_store=MEMORY`. На Windows провести проверку Process Monitor по [инструкции аудита](../security/network-audit.md) со служебными файлами SQLite, тестовой меткой и удалением заметки. Описать в SECURITY.md, что копия индекса может раскрывать слова и позиции и что после удаления на освобождённых страницах могут оставаться данные.

#### Как измеряется скорость поиска

26.11.2026 предварительно измерили FTS5 SQLite 3.54.1 на Windows. Генератор проекта создал 50 000 заметок с зерном 1. Одна таблица FTS5 без хранения исходного текста заполнялась в памяти по отсортированным путям. Замеры сделаны после первых 10 000 и после всех 50 000 файлов. Для запросов «проект», «отчёт», «план», «заметка», «работа» выбирались первые 50 совпадений по релевантности. На 10 000 медианы пяти повторов составили от 2,24 до 12,92 мс, на 50 000 — от 9,79 до 58,91 мс. Этот замер охватывает выборку SQLite. Обработка словоформ, чтение строк с диска и отрисовка окна входят в приёмку приложения.

- [ ] Для готового индекса на 10 000 первый экран результатов, до 50 строк, должен появляться за **≤ 200 мс** для каждого из пяти запросов по медиане пяти повторов. На 50 000 записать результаты тех же пяти запросов. На обоих объёмах дополнительно записать холодную постройку, повторное открытие, пик памяти, размер файлов базы и время до показа дерева. Сопоставить с Ctrl+O на той же машине и сборке. Сохранить действующие цели 0.2, включая дерево на 10 000 за ≤ 3 с.
- [ ] Добавить сценарий поиска в фильтр `tests/perf/vitest.config.ts` как для 10 000, так и для 50 000 заметок, включить его в обе строки матрицы CI. QA запускает `cargo test -p rhizomind --locked --release --lib -- --ignored perf_search`, затем `npm run test:perf -- search` с переменной окружения `RHIZOMIND_PERF_NOTES=10000` и повторяет с `RHIZOMIND_PERF_NOTES=50000`. Каждый фильтр должен выбрать тесты и напечатать количество заметок, запросы, все пять значений, медиану и вывод по цели. Если выбор движка не подтверждён, приложить сравнение с резервным вариантом из ADR перед сменой зависимости.

### 4. Вставка вложений

- [ ] Обработать два источника по явному действию пользователя через `src/editor`, `src-tauri/src/clipboard` и команды хранилища. Это существующий файл внутри хранилища или байты, которые ОС передала непосредственно, включая скриншот. Если доступен только внешний путь, показать предложение скопировать файл в хранилище средствами ОС. Отказ происходит до открытия или запроса атрибутов. Вставка обычного текста работает как прежде.
- [ ] Учесть настройку папок назначения по типам и папку заметки по умолчанию. Применять существующую проверку контура и создание без перезаписи. Вернуть различимый путь к созданному вложению. Ссылку вставлять в исходный документ по завершении записи. Если документ уже закрыт, показать путь сохранённой копии. Непредставимое в вики-ссылке имя требует выбора другого имени.
- [ ] QA выполняет `cargo test -p rhizomind --locked attachment`, `npm test -- attachment` и `npm run test:e2e -- attachment`. Проверяет вставку PNG из байтов ОС, файл в хранилище, внешний путь в буфере, тексте, диалоге и прямом вызове IPC, ссылку файловой системы за границу, коллизии, отсутствие папки, отмену, закрытие вкладки и отказ диска. Сравнивает байты источника и назначения, отсутствие ложной ссылки после ошибки и события Process Monitor для внешнего пути.

### 5. Просмотр встраиваний

- [ ] Распознавать `![[…]]` в существующей обработке живого предпросмотра и вики-ссылок. Учитывать исходный режим, блоки кода и существующий механизм разрешения имён заметок. Для повторяющегося имени картинки использовать различающий путь. Ошибочная, отсутствующая или неоднозначная цель показывает причину и сохраняет файловый состав. Переименование и обратные ссылки продолжают работать.
- [ ] Сделать один локальный просмотр картинок для дерева и заметки. Принимать только проверенные байты поддерживаемого формата, с ограничением размера и числа декодируемых пикселей до выделения памяти. Для заметок показывать один уровень и компактную ссылку дальше. Для прочих вложений показывать имя и тип. Внешние URL, активный SVG/HTML, повреждённое или чрезмерное изображение проверяются до отображения. Измеренные ограничения указать рядом с реализацией и в проверках границ.
- [ ] QA запускает `cargo test -p rhizomind --locked embed`, `npm test -- embed`, `npm run test:e2e -- embed` и `npm run check:network`. Проверяет PNG и JPEG из дерева и заметки, одинаковые имена, отсутствующую цель, одиночный и двухсторонний цикл, содержимое блока кода, перестановку файла между выбором и открытием, повреждённое изображение и границы лимитов. Сверяет снимки обеих тем и сетевой аудит.

### Приёмка выпуска

- [ ] На принятом коммите `npm run verify` проходит на Windows и Linux, включая оба запуска cargo deny. GitHub запускает `npm run test:e2e` и проверки скорости. Для каждого модуля QA прилагает ссылку на конкретный прогон, снимки и результаты для соответствующего коммита.
- [ ] Собрать `npm run package:portable` без WebDriver, записать SHA-256 и проверить запуск именно извлечённого архива. Владелец на второй машине открывает палитру, копирует шаблон, ищет и переходит к строке, вставляет скриншот, открывает картинку, проверяет скорость, установщик и сетевой аудит. Публикация следует после ручной приёмки.
