Ветка `task/3.2-ci-flakes` от main 0d79547. Данные — публичный API GitHub Actions: все запуски CI с 24.10 по 27.10.2026 (285 запусков; 259 заданий Windows и 266 Linux дошли до шага генератора), журналы заданий и артефакты `e2e-screenshots-Linux` упавших заданий (в них журнал tauri-driver).

**Распределение одной попытки** (строка `gen-vault: 10 000 заметок за … с`):

| | заданий | медиана | 90-й проц. | 95-й / 99-й проц. | максимум |
|---|---|---|---|---|---|
| Windows | 259 | 5,71 с | 8,95 с | 10,08 с | 58,61 с |
| Linux | 266 | 0,66 с | 0,90 с | 1,57 с (99-й) | 3,12 с |

**Медленная попытка — разовая.** После теста в том же шаге идёт прогон командной строки с той же работой (10 000 заметок); его время — длительность шага минус сборка и тест. В заданиях, где тест шёл 10–14,9 с, прогон командной строки шёл 4,0–7,6 с; ни в одном из 252 заданий обе попытки не превысили 10 с (худшая из лучших — 9,2 с). Значит, это помеха общей машины (NTFS, антивирус), а не медленный раннер целиком; повторный замер её снимает.

**Исправление** (`tools/gen-vault/tests/perf.rs`): лучшая из трёх попыток (останов на первой, что уложилась), все попытки — в журнал; пределы по распределению:
- Linux **1,5 с** = ×2,3 медианы. На Linux время — работа самого генератора, поэтому здесь ловится настоящий регресс кода ×2,3 и больше. Проверка: тот же тест на 30 000 заметок (×3 работы) — `медленно во всех попытках: 9.73 с, 13.41 с, 12.83 с (предел 1.5 с)`.
- Windows **12 с** = ×2,1 медианы, на 30 % выше худшей лучшей попытки (9,2 с). Время на Windows в основном уходит на файловую систему, регресс кода ×3 виден, ×2 — не всегда.
- Прежний предел 10/15 с по одной попытке не ловил на Linux даже ×10 (0,66 с против 10 с).

Модульные тесты выбора лучшей попытки (`best_of_*`) — в том же файле, идут в `npm run verify`.

## 2. Linux, сценарные тесты: «не создался сеанс WebDriver при перезапуске» (`UND_ERR_SOCKET`)

**Причина — гонка запуска tauri-driver, не программа.** tauri-driver 2.1.0 (`src/main.rs`) запускает драйвер движка (WebKitWebDriver) и сразу открывает свой порт, не дожидаясь готовности драйвера движка. `driver.ts` ждал только порт tauri-driver. Если запрос `POST /session` приходит раньше, чем WebKitWebDriver открыл свой порт, tauri-driver получает отказ и обрывает соединение клиента.

Во всех 5 случаях за период в журнале tauri-driver (артефакт) — ровно одна такая строка:

```
Error serving connection: hyper::Error(User(Service), client error (Connect)
Caused by:
    0: tcp connect error
    1: Connection refused (os error 111))
```

| Задание | Тест | Время теста |
|---|---|---|
| [122130799244](https://github.com/IvanMarCreator/Rhizomind/actions/runs/40486886904/job/122130799244) (3757e6b) | live-preview, перезапуск | 42 мс |
| [122085865743](https://github.com/IvanMarCreator/Rhizomind/actions/runs/40473462289/job/122085865743) (5adb060) | live-preview, перезапуск | 25 мс |
| 121756808168 (0eeecf3) | vaults, первый запуск | — |
| 121744329137 (daca238) | vaults | — |
| 121347853556 (d711050) | tree | — |

Тест падает за 25–42 мс — программа к этому моменту уже вышла, сессия рвётся на первом запросе. Замер (`gap.mjs`, 20 запусков tauri-driver): в момент, когда порт tauri-driver открыт, порт драйвера движка не готов в 19 из 20 запусков без нагрузки (ещё 0–7 мс) и в 20 из 20 под нагрузкой 8 процессов (ещё 24–93 мс). Обычно клиент успевает медленнее; под нагрузкой — нет.

**Исправление** (`tests/e2e/driver.ts`): `startApp` ждёт оба порта; если соединение всё же оборвалось (`UND_ERR_SOCKET`, `ECONNREFUSED`, `ECONNRESET`) и программа не запустилась — один повтор создания сессии с записью в журнал. Повтора нет, если процесс программы есть: второй запуск упёрся бы в замок одного экземпляра.

## 3. «Программа не завершилась за 20 с после закрытия окон» и «процесс программы один»

**Причина — гонка остановки драйверов, программа не зависает.** Воспроизведено локально (Linux, Xvfb, 4 процесса нагрузки на 2 ядра): тест с 25 перезапусками подряд (открыть заметку, ввод, конец сессии) — **8 из 25** раз программа после конца сессии осталась жить. Факты по каждому случаю:
- окно программы **показано** (`x11-titles.py`: «Заметка — Стресс — Rhizomind — ТЕСТОВАЯ СБОРКА (webdriver)»), то есть закрытия окна не было вовсе: цикл закрытия (решение 53) сначала скрывает окно и в любом случае уничтожает его через 10 с;
- стеки потоков (gdb): главный поток ждёт событий в `gtk_main_iteration_do` → `g_main_context_iteration` → `poll`, остальные потоки — в своих циклах ожидания; блокировок нет. Программа исправна и просто никем не закрыта.

Механизм: в нормальном случае WebKitWebDriver отвечает на `DELETE /session` и сразу завершает запущенную им программу (процесса нет уже через 10–100 мс после ответа). `driver.ts` сразу после ответа останавливал tauri-driver, а тот по SIGTERM убивает WebKitWebDriver (`Child::kill`, SIGKILL; tauri-driver 2.1.0, `src/server.rs`). Если это случается раньше, чем WebKitWebDriver завершил программу, программа остаётся сиротой с открытым окном. Проверка: с паузой в десятки миллисекунд между ответом и остановкой драйвера (запись в журнал) — **0 из 25**; с исправлением ниже — **0 из 40**.

Следы в CI: `программа не завершилась` (live-preview, 20 123 и 20 311 мс, ветка 2.10: 220a6de, 7dee19f — там же перед этим окно зависло на файле 11 МБ, ошибка ветки исправлена в 850c766) и `AssertionError: процесс программы один: expected [ 8261, 8598 ] to have a length of 1 but got 2` в `close.test.ts` (121724003432, 121734111829; лишний pid один и тот же во всех трёх тестах файла — программа, оставшаяся от предыдущего файла `vaults.test.ts`).

**Исправление** (`tests/e2e/driver.ts`, `stop()`): на Linux драйвер останавливается только после выхода программы этой сессии (до 10 с; иначе — строка в журнал, процесс не убивается, чтобы следующий тест упал с понятной причиной). На Windows не нужно: tauri-driver держит процессы в задании ОС с завершением при закрытии (`src/main.rs`, `limit_kill_on_job_close`). `waitForAppExit` пишет время выхода, а при неудаче — оставшиеся процессы (pid, состояние, сколько живёт) и какие были при начале ожидания.

Задания с `The action 'Сценарный тест (Linux)' has timed out after 10 minutes` (26–27.10, ветки 2.6, 2.8г и main 1567c9d) — все тесты зелёные, шаг упирался в прежний предел 10 мин; уже исправлено (предел 20 мин).
