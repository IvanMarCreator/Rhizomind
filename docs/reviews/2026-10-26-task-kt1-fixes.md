# Исправления по ручной проверке КТ1 (26.10.2026)

Владелец проверил сборку КТ1 (main a481e0f) руками — настоящей мышью и клавиатурой — и нашёл пять ошибок, которые автоматические тесты не поймали. Ветка `task/kt1-fixes`.

## 1. Перетаскивание в дереве не работает (курсор «запрещено»)

**Причина.** Tauri на Windows по умолчанию ставит свой перехватчик перетаскивания (wry `DragDropController`, `vendor/wry/src/webview2/drag_drop.rs`): `RevokeDragDrop` + `RegisterDragDrop` на дочерних окнах WebView2 — обработчик WebView2 подменяется своим, который понимает только файлы ОС (`CF_HDROP`) и для всего остального отвечает `DROPEFFECT_NONE`. Документация `WebviewWindowBuilder::disable_drag_drop_handler` в tauri 2.12.5 прямо говорит: без выключения HTML5 drag and drop на Windows не работает. Разметка дерева (`draggable`, `dragstart`/`dragover` с `preventDefault` и `dropEffect = 'move'`) была верной.

**Исправление.** `.disable_drag_drop_handler()` в `build_window` (`src-tauri/src/lib.rs`). Перехватчик Tauri заодно не давал бросать в окно файлы извне. Первая попытка заменить это настройкой движка `AllowExternalDrop = false` провалилась: проба CI (ветка `task/kt1-fixes-probe2`, CI 40368935440) показала, что в оконном режиме WebView2 она выключает и перетаскивание внутри страницы (`dragstart → dragend:none`; с `true` — `dragstart, dragenter, dragover, drop, dragend:move`). Поэтому запрет бросков извне — в интерфейсе: `src/shell/externalDrop.ts` (ставится в `src/main.ts`) принимает только перетаскивание, начатое на странице (был `dragstart`), остальное гасит в фазе перехвата на документе до любых обработчиков — и дерева, и CodeMirror (он умеет вставлять содержимое брошенного файла). Брошенный файл движок открыл бы как `file://` — переход и так запрещён ядром. Отражено в `docs/SECURITY.md` («Файлы»), с ограничением: запрет — в коде интерфейса, а не в движке.

**На решение (ИБ).** Запрет бросков извне раньше держал перехватчик Tauri в ядре, теперь — код интерфейса. Альтернатива на уровне ядра — свой `IDropTarget`-обёртка над обработчиком WebView2, пропускающая только перетаскивания из своего процесса; это заметный объём Win32-кода. Рекомендация: оставить как есть (сети нет ни в одном варианте; бросок — действие пользователя), вернуться при ревью ИБ.

**Почему тест не поймал.** `tests/e2e/tree.test.ts` шлёт события HTML5 скриптом (`dispatchEvent(new DragEvent(...))`) — мимо цикла перетаскивания Windows (OLE `DoDragDrop`), а ломался именно он. Действия WebDriver события перетаскивания HTML5 не порождают. Новый тест — в `src-tauri/tests/webview2_runtime.rs` (`check_real_drag`): в живом окне WebView2 элемент тянется настоящей мышью (`SendInput`), страница должна получить `drop`; На коде без исправления тест красный в CI Windows (коммит 74d131f, CI 40357650513): «перетаскивание мышью внутри страницы не дошло до drop: события "dragstart"» — ровно симптом владельца.

## 2. Tab в быстром переходе уводит фокус

**Причина.** Обработчик Tab висел только на поле и узнавал клавишу только по `key === 'Tab'`. Он не срабатывает, если (а) фокус в момент нажатия не в поле или (б) движок присылает для Tab другое значение `key`. Проба на коде main (ветка `task/kt1-fixes-probe`, сценарный тест без исправлений, CI 40358135115):
- Linux (WebKitGTK): Tab работает, а **Shift+Tab уводит фокус** в текст заметки — `key` у Shift+Tab там не «Tab» (GTK присылает `ISO_Left_Tab`), `code` — «Tab». После этого и Esc не закрывает окно: фокус уже не в поле.
- Windows (msedgedriver): клавиши WebDriver ошибку **не воспроизвели** — Tab и Shift+Tab там приходят с `key = 'Tab'`.

На компьютере владельца точную причину по CI установить нельзя. Известные пути, при которых настоящая клавиатура в WebView2 даёт тот же симптом: ввод через службу текста Windows (подсказки при вводе с физической клавиатуры, IME) — `key = 'Process'`, `isComposing = true` (старый код выходил по `isComposing` ещё до проверки Tab); фокус не в поле (окно было без фокуса ОС — см. п. 3 — или фокус ушёл кликом). Исправление закрывает все эти пути; ручная проверка владельцем обязательна.

**Исправление.** Tab и Shift+Tab перехватываются обработчиком на `window` в фазе перехвата, пока окно открыто, — где бы ни был фокус и до любых других обработчиков; клавиша узнаётся и по `code` (`isTabKey`, `src/quick-switcher/keys.ts`): при вводе через службу текста Windows (подсказки, IME) `key` приходит как «Process». Фокус, ушедший из окна быстрого перехода (`focusin` вне диалога), возвращается в поле. Tab без модификаторов подставляет имя пункта, выбранного стрелками; если стрелками ничего не выбрано — первого пункта (он выделен по умолчанию). На пункте «Создать заметку» — ничего (как было).

**Почему тест не поймал.** Компонентный тест отправлял `keydown` прямо в поле: он не проверял, где фокус в момент нажатия, и не проходил через обработку клавиш движком. Новые тесты: компонентные (Tab при фокусе вне поля; `key = Process`, `code = Tab`) и сценарный `tests/e2e/quick-switcher.test.ts` — клавиши через WebDriver (msedgedriver), открытие по Ctrl+O из редактора и кнопкой на ленте.

## 3. Окно первого запуска позади Проводника, без фокуса

**Причина.** На Windows окно создаётся скрытым и показывается только после проверки InPrivate у живого движка — через заметное время после запуска; Windows к этому моменту не даёт окну передний план, и оно оказывается позади Проводника.

**Исправление.** После `show()` (и разворота) — `set_focus()` (tao: `SetForegroundWindow`, при отказе — штатный приём tao с нажатием Alt). Касается всех окон из `build_window`: окна управления и окон хранилищ при запуске. Проверка — `check_foreground` в `webview2_runtime.rs`; **красной она не была**: на раннере CI окно и без исправления выходит вперёд (тест запускается из консоли, у которой есть право переднего плана; запуск из Проводника — другой случай). Тест охраняет от регресса, но доказательство исправления — только ручная проверка запуска из Проводника.

## 4. Обрезанное пояснение у неактивного «Создать заметку» с «/»

Пояснение «Косая черта в имени недопустима: сначала создайте папку» стояло в той же строке с `max-width: 55%` и многоточием. Теперь — второй строкой под названием пункта, с переносом, целиком (`QuickSwitcher.svelte`). Проверка — сценарный тест (`scrollWidth`/`scrollHeight` не больше видимой области) и снимок `switcher-create-blocked`.

## 5. Шестерёнка «Настройки» не реагирует

Окно настроек — задача 2.8б после КТ1. Кнопка на ленте теперь явно неактивна: `aria-disabled="true"`, приглушённый вид без подсветки при наведении, подсказка из словаря `shell.ribbon.settingsLater` — «Настройки появятся в следующей версии» (`src/shell/Ribbon.svelte`). Когда оболочка передаст `onSettings`, кнопка станет обычной.

## Владельцу проверить руками

1. Дерево: перетащить заметку в папку и папку в другую папку — курсор «переместить», элемент переносится. Перетащить файл из Проводника в окно (на дерево и в текст заметки) и текст из другой программы — не принимается (курсор «запрещено»), ничего не происходит.
2. Запуск двойным щелчком из Проводника: окно (управление хранилищами или хранилище) появляется поверх Проводника и сразу принимает ввод с клавиатуры.
3. Ctrl+O из открытой заметки и кнопкой на ленте: Tab сразу (без стрелок) подставляет первое имя; стрелка вниз + Tab — выбранное; Tab и Shift+Tab много раз подряд — фокус остаётся в поле. В русской раскладке тоже.
4. В быстром переходе набрать `Папка/Имя` — пояснение под пунктом видно целиком.
5. Шестерёнка на ленте приглушена, при наведении — «Настройки появятся в следующей версии».
