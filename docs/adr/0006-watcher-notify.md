# ADR 0006. Слежение за папкой: notify 9 в ядре Rust

Статус: принято 24.10.2026. Заменяет прежнюю редакцию (@parcel/watcher, до ADR 0008).
Основание: [исследование крейтов Rust](../research/2026-10-24-rust-crates.md).

## Контекст
Пока приложение открыто, изменения в папке хранилища (Проводник, другой редактор, Git) должны попадать в дерево и в открытую заметку за секунду, а внешние изменения — никогда не затираться (инвариант 4). Слежение работает с 0.1, с 0.2 по нему обновляется индекс. Ядро теперь на Rust (ADR 0008).

На Windows уведомления идут через `ReadDirectoryChangesW` с буфером фиксированного размера. При всплеске событий буфер переполняется, и события теряются. Главное требование: потеря не должна быть молчаливой.

## Решение
- **Крейты:** `notify` **9.0.0-rc.6** (CC0-1.0) и `notify-debouncer-full` **0.8.0-rc.2**. Версии фиксируются точно (`=9.0.0-rc.6`): это кандидаты в выпуск, обновление — отдельным решением с прогоном нагрузочных тестов.
- **Один наблюдатель на хранилище**, рекурсивно на корень (один дескриптор на всё дерево).
- **Склейка событий** — `notify-debouncer-full`: собирает пары «старое имя — новое имя» в переименование и гасит дребезг при сохранении.
- **Rescan → полная сверка с диском.** Когда ОС сообщает о переполнении, `notify` присылает событие Rescan (в 8.2.0 переполнение терялось молча; исправлено в rc.5). Ядро в ответ заново обходит хранилище и сверяет с моделью: появившиеся, исчезнувшие и изменённые файлы. Массовые операции (`git checkout`, распаковка архива) почти всегда идут этим путём.
- **Фильтр `.rhizomind/`** — в своём обработчике событий: всё внутри служебной папки отбрасывается до склейки. `notify` исключений путей не поддерживает.
- **Свои записи** ядро узнаёт по версии файла: хэш содержимого `blake3` + размер + дата изменения. После своей записи ядро запоминает новую версию; событие о файле с такой версией не считается внешним изменением.
- **Переименование и перемещение снаружи** распознаются по идентификатору файла NTFS (крейт `file-id` 0.2.3, 128-битный FileId). Если пара событий не склеилась, ядро ищет исчезнувший файл с тем же идентификатором, затем — с тем же размером и хэшем.
- **Сверка при открытии хранилища** — по дате изменения и размеру, как и раньше.

## Требования к поведению (без изменений с прежней редакции)
С 0.1 слежение покрывается автотестами под нагрузкой в Rust (`cargo test` на `windows-latest`): создание и изменение 10 000 файлов пачкой, переименования, замена множества файлов как при `git checkout`, искусственное переполнение. Критерий: после затихания событий модель совпадает с диском; свои записи не дают ложных конфликтов; внешнее изменение при несохранённых правках всегда даёт конфликт.

## Запасной путь
Если `notify` 9 на Windows ведёт себя не так, как в исходниках и тестах, — свой наблюдатель на `ReadDirectoryChangesW` через крейт `windows` 0.62 за тем же интерфейсом модуля VaultWatcher. Остальное ядро о замене не узнаёт.

## Последствия
- Нативных модулей Node больше нет: слежение — обычный код Rust в процессе ядра, сетевого кода в нём нет (проверка `cargo deny` и `cargo tree`, ADR 0009).
- Атомарная запись через замену файла меняет идентификатор NTFS и, возможно, дату создания. Разрешение дублей имён идёт по дате создания (спецификация 0.1, С3.4), поэтому запись использует `ReplaceFileW` или ядро хранит «дату появления» заметки — решается в задаче хранилища.
- Кандидат в выпуск — риск: при переходе на стабильную 9.0 повторяем нагрузочные тесты.

## Отклонено
- `notify` 8.2.0 (стабильная): переполнение на Windows теряется без сообщения.
- Сразу свой наблюдатель на `windows`: больше своего кода без нужды; оставлен запасным путём.
- `@parcel/watcher` (прежняя редакция): нативный модуль Node, неприменим после перехода на Tauri.

## Уточнение 25.10.2026: дата создания при атомарной записи

«Самая старая» заметка при дубликатах выбирается по дате создания файла (С3.4), а при равной дате — по пути в естественном алфавитном порядке. Атомарная запись не должна сдвигать дату создания:
- **Windows:** замена файла через `ReplaceFileW` — сохраняет дату создания и идентификатор файла NTFS заменяемого файла;
- **macOS:** дата создания переносится на новый файл;
- **Linux:** дата создания (`statx` birth time) после замены файла может сдвинуться — «самая старая» может смениться после правки. Известное ограничение до перехода на Linux; при переходе решается хранением «даты появления» в индексе.

Свои записи наблюдатель узнаёт по хэшу и размеру, которые vault регистрирует **до** замены файла (дата изменения известна только после).

## Уточнение 25.10.2026: распознавание переименования и недоступность хранилища (задача 1.4)

- **Без кэша идентификаторов `notify`.** Склейка событий идёт с `notify_debouncer_full::NoCache`: штатный кэш (`FileIdMap`) обходит дерево с переходом по ссылкам и выходил бы за контур хранилища через точку соединения. Переименования распознаёт своя модель дерева ядра.
- **Идентификатор подтверждается.** Совпадение `file-id` для файла принимается, только если совпадают и размер, и дата изменения (на FAT/exFAT и при переиспользовании inode id может достаться другому файлу). Запасной путь — единственный исчезнувший кандидат с тем же размером и датой изменения, без сравнения хэша (отступление от первоначального «размер и хэш»: хэш исчезнувшего файла уже не прочитать). Если подтверждения нет — «исчез» + «появился». Папка считается перенесённой, если она пуста или подтверждён хотя бы один её файл.
- **Недоступность ≠ удаление.** Если корень хранилища пропал или к нему нет доступа (отключённая флешка, сетевая папка), изменений не выдаётся, модель не трогается, интерфейс получает сигнал «хранилище недоступно»; при возвращении — «доступно» и полная сверка. Ошибка чтения отдельной папки (кроме «не найдено») оставляет её поддерево как было до повторной сверки.
- **Свои записи** — журнал из нескольких последних версий на путь (до 4, 120 с); событие подавляется только если на диске побайтно своя версия (размер и хэш).
